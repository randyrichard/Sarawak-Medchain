# Full audit, 7 October 2026

A second whole-product check, after photo storage, the Safari work and the Cloudflare demo
went in. It covers bugs, errors, data, the frontend, and layout on desktop and on iPhone and
Android sizes. Everything marked **Fixed** has a test that fails without the fix, or was
re-checked in a browser, or both.

## How it was checked

| Pass | What was done |
|---|---|
| Automated | Full API suite (1,550 tests) and web suite (595), both typechecks, both builds, the bundle credential scan on a build made without `.env.local`, the demo build, `npm audit` on production dependencies, a schema drift check |
| Data | A freshly built database (base seed and demo data), then SQL checks: row-level security on every table, status against timestamps for incidents, actions, permits, inspections, audits and visitors, cross-company references, duplicate reference numbers, stored photo counts against stored files, the file integrity check, and the dashboard's numbers against counts taken directly from the tables |
| Desktop | Playwright and Chromium against that database, every page, tab, dialog and drawer, as admin, employee, HSE manager, supervisor and CEO, at 1280×800, 1440×900 and 1920×1080, light and dark: **844 screen states**. Each one measured overlap, clipping, text running out of its box, sideways scroll and blocked views, and ran axe-core (WCAG 2.2 A/AA, including colour contrast) |
| Mobile | The repository's own phone audit (`npm run audit:mobile`: iPhone SE, iPhone 14 Pro, Pixel 7, Galaxy S8, iPhone SE landscape, with the keyboard up), then the same deep crawl on iPhone SE, iPhone 13, iPhone 14 Pro Max, Pixel 7, Pixel 7 landscape and Galaxy S8 for six roles: **1,078 screen states**. Then six workflows driven by touch on an iPhone SE profile: report an incident, report a near miss with a photo, a corrective action from creation to verification, an inspection that raises a defect, inspection photos stored byte for byte, and an audit photo filed against its checklist item |
| Code review | Everything added since the last audit (photo storage, the Safari changes, the demo build), and the permit, incident and investigation rules the crawl led to |

The browsers are Chromium at each phone's size, touch and user agent. That is how Android
renders; it is not Safari. A real iPhone is still needed (`GO_LIVE.md` §3).

## What was found

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | **A permit could be approved after its working window had ended.** Neither the approval nor the staged review chain checked the time. The approver signed, and the permit showed as Expired the moment it was signed: a signed approval that authorised nothing. Starting work was already refused. | Medium | **Fixed.** Approval and every review stage refuse, and say to send it back for new dates. Tests: `permitService` and `permitReview` integration tests. |
| 2 | **Inspection results and audit findings showed photos that do not exist.** Before photo storage, the runners saved the number of photos picked and threw the photos away. Those counts are still on rows written before then, and the results screen shows them as "2 photo(s)". The demo data did the same for every completed inspection. | Medium | **Fixed.** Migration `20261008090000_photo_counts_from_storage` sets each count from the photos actually stored (12 of 12 corrected on the audit database; no schema change). Demo data fixed. |
| 3 | **A failed batch of photos was reported as all of them failing.** Photos go five to a request. With seven, if the second request failed, the screen said "7 photos did not upload. Add them again", although five were stored. Doing what it said put those five on the safety record twice. "Add photos" on a saved record also kept all seven selected, so pressing Upload again sent the five again. | Medium | **Fixed.** Each batch stands alone. Only the photos that did not arrive are reported and kept selected. Tests: `fieldEvidence.dom.test.tsx`. |
| 4 | **An incident could be dated in the future.** One dated June 2027 was accepted. It sorts to the top of the register, makes "days since the last incident" negative, and is counted in a month that has not happened. | Medium | **Fixed.** The server refuses a time more than 15 minutes ahead (a fast phone clock is allowed), for the forms and the public API alike. | 5 | **The investigation form was editable by roles that may not record one.** An Executive could type a direct cause and a root cause, and the save on leaving the field came back "Your role does not permit recording an investigation". The same for the people involved and linked equipment. | Medium | **Fixed.** Read-only for those roles, with one line saying who records it. A test pins the web's list of roles to the server's. The figure was sized to the screen, and at exactly that width the row turns six-up beside the sidebar. | Low | **Fixed.** The figure is sized to its tile. Test: `people.test.ts`. |

## Checked and fine

- **No JavaScript or console errors** in any of the 1,922 screen states, desktop and phone,
  and **no colour-contrast failures** in light or dark mode. (The crawl does not count a
  refused request, a 401 or 403, as an error; the workflows do, which is how finding 10 was
  caught.)
- **No sideways scrolling, overlapping text or blocked views** on any page at any size. The
  repository's phone audit, which also checks fields with the keyboard up, found nothing.
- **The dashboard's numbers match the database**: open, closed, high-risk and investigating
  incidents, open, overdue and awaiting-verification actions, and active and submitted permits.
- **No row points at another company's site or asset**, and no reference number is used twice.
- **Every stored file still matches the checksum recorded when it was uploaded.**
- **Row-level security** covers every table with a company column except four that are read
  while signing in, before the company is known. That is stated in the migration that added
  it. Child tables are reached through a protected parent.
- **Dependencies**: the API has no known vulnerabilities. The web has one advisory, an open
  redirect in React Router through a backslash. SafeChain's own redirect guard
  (`safeRedirect.ts`) already refuses any path with a backslash, and names the advisory. The
  other half of the advisory is server rendering, which SafeChain does not use.
- **The demo build** contains no API address and not the API seed's password; a customer
  build contains neither the demo accounts nor any password.

Not a problem, on inspection: the Executive's "Record findings" is disabled on purpose and
says who may do it; administration menu items sit edge to edge as a vertical list does; the
"Show password" button joins its field by design.
