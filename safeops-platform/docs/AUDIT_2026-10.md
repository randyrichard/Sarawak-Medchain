# Full audit, October 2026

A whole-product check after the go-live work. It covers bugs, errors, function, accessibility
and colour, and ethics and data honesty. Everything marked **Fixed** has a test that fails
without the fix, or was re-checked in a real browser.

## How it was checked

| Pass | What was done |
|---|---|
| Automated | Full API suite (1,530 tests) and web suite (551), typecheck, both builds, the bundle credential scan, the compose check, `npm audit` on production dependencies |
| Browser crawl | Playwright and Chromium against a freshly seeded database. Every page and tab was visited as admin, employee, supervisor and CEO, in light and dark mode at desktop width, and in light mode at phone width (390 px). That is 712 page views. Each recorded console errors, failed API calls, sideways overflow, and an axe-core WCAG 2.1 A/AA scan, including colour contrast. |
| Code review | Data loading and error handling, switching company, empty-data maths, and authentication on every API route (probed without a token) |
| Ethics and honesty | Claims the product makes, fabricated or alarmist data, anonymity of reports, the privacy notice, and how the demo presents itself |

## What was found

### Bugs

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | **Switching company in the admin console kept the previous company's data on screen.** On Security → Authentication Policy, pressing Save then wrote the previous company's password and session rules into the new company. Only admins who belong to more than one company are affected, such as the demo admin. | High | **Fixed.** The console rebuilds its section for each company. Test: `AdminPage.dom.test.tsx`. |

### Accessibility and colour

Across all 712 page views, axe-core found **no** violations in dark mode, and **two** in light
mode. Both were contrast failures on tinted backgrounds:

| Element | Was | Now |
|---|---|---|
| Amber "Not yet held" on the Toolbox page (`--warning` on `--warning-soft`) | 4.46 : 1 | `--warning` `#946603` → `#8a5e02`: 5.05 : 1 |
| Grey "1 user(s)" on a selected role row (`--muted` on `--accent-soft`) | 4.21 : 1 | `--muted` `#716f69` → `#6b6963`: 4.60 : 1 |

Both tokens were checked against white, the page background and every tint, and pass 4.5 : 1
on all of them. The re-crawl after the change found no violations. Nothing scrolls sideways at
phone width on any page, for any role.

### Ethics and data honesty

| # | Finding | Status |
|---|---|---|
| 11 | **Every failed sign-in was called "suspicious" and rated critical.** One mistyped password a month raised a critical finding advising to "block the source". Alarm on every typo teaches administrators to ignore the Security Center. | **Fixed.** A few failures are a warning, ten or more are serious, and fifty or more, or an account locked out, are critical. "Unusual" in the login history now means only an attempt on a locked, deactivated or suspended account. Tests: `failedSignInSeverity.test.ts`, and the updated admin integration test. |
| 12 | **The "Suspicious logins" tile said "last 7 days"; the server counted 30.** | **Fixed.** The tile is now "Failed sign-ins, last 30 days". |
| 13 | **The login history had a Location column and a map pin**, implying SafeOps detects unusual locations. **It doesn't:** the column was always empty from the API, and the offline demo filled it with invented places ("Amsterdam, NL"). A demo should never show a capability the product doesn't have. | **Fixed.** The column, pin and invented locations are gone, from the CSV export too. The real reason is shown instead, e.g. "Tried a locked account". |
| 14 | **The offline demo shows realistic invented companies, people and injuries with no label**, and nothing typed in it is saved | **Fixed.** A "Demo mode, made-up sample data" note on every screen when no API is configured |
| 15 | **Webhooks were described as "real-time".** They are sent by a queue checked every 30 seconds. | **Fixed.** Now "usually within 30 seconds" |
| 16 | **`llms.txt` said there is no public API**, but there is a key-authenticated integration API (`/v1`). It also pointed to a "contact route" on the sign-in page that does not exist. | **Fixed** |

## Checked and fine

- **Restricted pages:** lower roles see "You don't have access to this page", not a crash or a
  blank screen.
- **Refused people lists:** supervisors' people lists fall back to the employee register when the
  member list is refused. The refusal is deliberate, and the console shows it as a 403.
- **Raw HTML:** the only raw HTML is QR-code SVG generated locally from a fixed address, so it is safe.
- **Empty lists:** every `Math.max(...list)` and `Math.min(...list)` on data that can be empty is guarded.
- **Privacy notice:** in English and Bahasa Malaysia as section 7(3) of the PDPA requires, and
  clearly marked as a draft that is not in force.
- **Blame:** no ranking of individual people by incidents. The site comparison compares sites.

## Still open: decisions or larger work

| Item | Why it is not fixed here |
|---|---|
| React Router 7 | A major-version upgrade, to clear the last moderate advisory. The exposed path is already guarded (see 10). |
| 59 remaining calls with no error branch, mostly refreshes after a save | Spread across 38 files. A failed refresh after a save leaves the old list on screen, which is safer than the first-load case fixed above. Convert to `useAsync` as files are next touched. |
| Publishing the privacy notice | Needs your hosting country (PDPA s129) and a lawyer's review (`GO_LIVE.md` §2) |
| A 401 in the console on signed-out pages | The app checking for a session. Correct behaviour, but it shows as a red console line. Cosmetic. |
